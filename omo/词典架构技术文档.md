# 腕上词典 — 离线词典架构技术文档

> 本文档描述腕上词典在手环端离线词典的全部搜索逻辑、索引构建方式、环境限制和架构约束。供评估压缩优化方案使用。

## 一、环境限制

### 1.1 硬件平台

| 项目 | 值 |
|------|-----|
| 目标设备 | Xiaomi Band 10（主要） |
| 屏幕 | 212 × 520 px，跑道屏（非圆形） |
| 设计尺寸 | `designWidth: "device-width"`（运行时自适应） |

| RAM | 典型值 ~64–128MB（系统 + 应用共享，无明确 API 获取上限） |
| 存储 | flash 存储，RPK 安装后解压到应用沙箱 |

### 1.2 软件平台

| 项目 | 值 |
|------|-----|
| 框架 | Xiaomi Vela JS QuickApp |
| JS 引擎 | JSC（JavaScriptCore）字节码 |
| 工具链 | `aiot-toolkit` v2.0.5 / `rspack` v1.7.12 |
| 最小平台版本 | `minPlatformVersion: 1000` |
| 文件 API | `@system.file.readText()` — 异步读取文本文件 |
| 存储 API | `@system.storage` — 键值对存储（JSON），~100KB 级别 |
| 路由 API | `@system.router` — `push` / `replace` / `back` |

### 1.3 运行时限制（推断 + 官方最佳实践）

- **无法使用 SQLite / 数据库** — 无原生 DB 支持
- **无网络** — 纯离线，所有数据内置在 RPK 中
- **无 mmap / 大文件映射** — 文件必须通过 `file.readText()` 全量读入内存
- **单次 readText 推荐上限** — 官方隐含建议单文件不超过 40KB
- **热路径限制** — `touchmove`、列表滚动、搜索结果渲染中避免分配
- **渲染能力** — 1 个 `list` 组件 + 20 条 `list-item` 基本够用
- **RPK 大小** — 当前调试版 2.76 MB，发布版约 2.3 MB；平台无硬性上限但越大安装越慢
- **内存** — 没有明确 API 报告可用内存；实测词库全量加载（约 5.2MB 解压数据）后可正常搜索和渲染

## 三、英文搜索索引（words/）

### 3.1 文件结构

26 个文件：`word_a.txt` ~ `word_z.txt`，按首字母分片。

### 3.2 行格式

```
<prefixLen,suffix>\t<entryId(base36)>\t<tagCode(hex)>
```

示例（word_a.txt）：
```
0,a	0	3
1,bandon	1	de
7,ed	2	40
...
2,dicate	a	c0
3,omen	b	10
```

- **前缀压缩**：每行只存与前一词不同的后缀。`prefixLen` 是重用前一词的前缀字符数，`suffix` 是追加部分。例如 `ear` → `2,r`（重用前词 "early" 的前 2 个字符 "ea"，追加 "r"）
- **entryId**：统一用 **base36** 编码（见 `generate_watch_dict.py` 第 646 行 `to_base36(entry_id)`）。这是本文档最关键的编码细节——后文搜索端必须用 base36 解析
- **tagCode**：8 种考试标签按 bitmask 编码为 hex 字符。`z`=中考(bit0) … `e`=GRE(bit7)

### 3.3 构建方式

```
rows = csv 读入（按原始顺序）
对 26 个字母分组：
  对每组按 word 字母序排序
  每行生成 prefixLen 压缩格式
  写入 word_<letter>.txt
entry_id = enumerate index（0..14941）
```

### 3.4 运行时搜索流程

```
performSearch(query):
  shards = getCandidateShards(query) → ["e"]（仅首字母）
  collectShardResults(["e"], query):
    readText("word_e.txt")
    collectCompactWordCandidates(text, query):
      逐行解码前缀压缩 → 恢复完整 word
      lower.indexOf(query) === 0 ? 保留 : 跳过
      最多 20 个 → candidates[{entryId, word, tag}]
    hydrateCompactCandidates(candidates):
      entryShardFor(entryId) → "00".."29"
      loadEntryShard(shard) → 读 entry_<nn>.txt
        entries = {}; 每行 entryId = baseId + lineIndex
        return entries
      对每个 candidate: item = entries[candidate.entryId]
      resultCard = { word: item.word, translation: ..., phonetic: ..., tag: ... }
```

**关键方法**：

```
getCandidateShards(query) → [query[0]]  // 仅首字母
collectCompactWordCandidates(text, query, candidates, seen, source, limit):
  if source: lower === normalizedQuery  // 精确匹配（变形用）
  else:      lower.startsWith(normalizedQuery)  // 前缀匹配
```

## 四、词条数据（entries/）

### 4.1 文件结构

30 个文件：`entry_00.txt` ~ `entry_29.txt`。每 500 个 entryId 一个分片。

### 4.2 行格式

```
<word>\t<phonetic(IPA编码)>\t<translation(词组编码)>\t[tagCode(hex)]
```

示例：
```
each	i:tS	#每个, 每一; %每个; *每个, 个人, 各自	3
```

- **音标编码**：IPA 字符映射为 ASCII 安全编码。如 `ə`→`a`、`ˈ`→`'`、`ɛ`→`e`
- **词组编码**：常见词性标记替换为单字符。如 `vt. `→`!`、`n. `→`@`、`[计]`→`{`
- **entryId 是隐式的**：entryId = `baseId + lineIndex`（0-based），不存储在行内容中。运行时 `loadEntryShard` 用此规则重建 `entries[entryId]` 映射

## 五、中文搜索索引

### 5.1 汉字索引（zh_index/）

64 个文件：`zh_00.txt` ~ `zh_3f.txt`。

**bucket = `ord(汉字) % 64`**，格式化为 2 位 hex。

**行格式**：
```
<汉字>\t<delta-base36-ids>
```

示例（zh_00.txt）：
```
一	0,z,1,4,c^5,1f,...
```

**delta-base36 编码**：
- entryId 列表按递增排序
- 差值 = `current - previous`（第一个 token 就是第一个 entryId）
- 每个差值用 base36 编码
- 连续相同差值用 RLE：`value^count`
- 运行时严格解码：`current += int(token, 36)`，RLE 展开 `^count`

严格性：零差值（除了第一个 token）、非递增、非法 base36 字符都将返回 `[]`。

### 5.2 中文词组索引（cn_index/）

64 个文件：`cn_00.txt` ~ `cn_3f.txt`。同样用 `ord(首字) % 64` 分桶。

**构建来源**：
1. ECDICT 翻译文本中提取中文词组（`re.sub(r'\[.*?\]', '', translation)` 去除括号内容，`re.sub(r'[a-zA-Z0-9]', '', ...)` 去英文，按标点拆分）
2. CC-CEDICT 扩充：取每个中文词组的英文释义，找到释义中的 ECDICT 英文词，反向映射到 entryId

**行格式**（同 zh_index 增加前缀压缩）：
```
<prefixLen,suffix>\t<delta-base36-ids>
```

示例（cn_00.txt）：
```
1,会	37,5k,95,...
```

### 5.3 运行时中文搜索

```
performSearch(query):
  hasChinese(query) → true → collectCn2EnResults()

collectCn2EnResults(query):
  firstChar = getFirstChineseChar(query)
  bucket = zhBucketFor(firstChar)  // ord % 64
  loadCnIndex(bucket):
    readText("cn_<bucket>.txt")
    prefixed decode + delta-base36 decode → {phrase: [entryId, ...]}
  ids = indexMap[query]  // 精确匹配
  if !ids: 前缀匹配回退（最多 20 key, 10 ID/key, 50 总量）
  fetchEntriesByIds(ids):
    按 entryShard 分组批量读取 entry 数据
    去重后最多 20 条 results
```

## 六、变形搜索（inflect/）

### 6.1 文件结构

两套索引：

| 目录 | 文件数 | 分片键 | 格式 |
|------|--------|--------|------|
| `inflect/` | ~256 个 | `key_for(form)` 2 字符 | `form\tbase1,base2,...` |
| `inflect_eid/` | ~256 个 | `form_eid % 256` 各存储 | `formEid(base36)\tbaseEid1,baseEid2,...` |

`key_for()` 取单词前 2 个字母数字字符，不足补 `_`。

### 6.2 变形关系来源

| 来源 | 覆盖 | 示例 |
|------|------|------|
| ECDICT exchange 字段 | ~2,000 | `ran` → `run`, `better` → `good` |
| BNC/COCA 词族表 | ~500 | `actuality` → `actual` |
| 后缀规则（`derived_candidates`） | ~400 | `happily` → `happy`, `movement` → `move` |
| WordNet 派生关系 | ~300 | `creation` → `create` |

### 6.3 运行时变形搜索

```
collectInflectResult(query):
  if query.length < 2: return  // 太短不查
  shard = keyFor(query)  // 如 "run" → "ru"
  readText("inflect_<shard>.txt") → 找 form=query → bases
  collectBaseResults(bases, results)
    // 在 words/ 中找 base 的完整词条
  collectReverseInflectResult(query)
    // 读 ireverse_<shard>.txt → 找 base=query → forms
    collectFormResults(forms)
      // 在 words/ 中找每个 form，找不到则从 baseWord 继承释义
```

## 七、模糊搜索

### 7.1 触发条件

```
finishEnglishSearch:
  results.length === 0
  && query.length > 2
  && searchMode !== "inflect"
  && isEnglishWord(query)
```

### 7.2 算法

编辑距离（bounded Levenshtein）：
- 最大编辑距离 = 2
- 扫描候选：所有字母分片 + 同首字母优先
- 扫描上限：4,000 词
- 候选池上限：80 词
- 返回上限：20 词
- 排序：距离 → 考试标签得分 → 词长

```
getFuzzyShards(query): [firstLetter] + [a...z]
scanFuzzyWordText(text):
  for each word:
    |word.length - query.length| > 2 → skip
    editDistanceBounded(query, word, 2) > 2 → skip
    candidates.push({word, distance, score})
score = 80 - |word.length - query.length| * 8
       + (同首字母 ? 20 : 0) + 标签加分(zk+40,gk+36,cet4+30,...)
```

## 八、entryId 编码说明（⚠️ 重要）

所有 word 文件中的 entryId 都使用 **base36 编码**，因为：
```
# generate_watch_dict.py 第 646 行
to_base36(entry_id),
```

但在之前的运行时代码中，`parseEntryId` 错误地将纯数字的 entryId（如 `"381"`、`"10"`）解析为十进制而非 base36，导致：
- "each" 的 entryId `"381"`(base36=4177) → 被解析为 381 → 指向 entry_00.txt[381] = "alarm"'s 数据 ❌
- "earplug" 的 entryId `"38a"`(含字母) → 正确解析为 base36 4186 ✓

**此 bug 影响所有 word 文件中 entryId >= 36 且全数字的 entryId（即 `"10"` ~ `"zz"` 中的纯数字段）。** 已于 2026-07-17 修复。

## 十、已知架构局限与优化空间

### 10.1 当前局限

| 问题 | 说明 |
|------|------|
| **cn_index 体积过大** | 47.2% 的字典体积（2.09 MB），因为每个中文词组存了一组 entryId。大量词组只有英文有但中文无对应的冗余映射 |
| **entry 数据未压缩** | 30 个 entry 分片共 1,043 KB（23.5%）。音标编码和词组编码只是简单字符映射，没有通用压缩 |
| **words/ 前缀压缩收益有限** | 仅 194 KB（4.4%），压缩率已经很高；优化空间不大 |
| **inflect 双索引** | `inflect/` + `inflect_eid/` 双套存储，~380 KB。eid 版实际未在搜索端使用 |
| **全量读入** | `file.readText()` 每次读整个文件，无法部分读取 |
| **cn_index delta-base36 + RLE** | 已做差值 + 游程编码，但 entryId 范围大（0~14941），差值 base36 编码后平均每个 ID 约 2-3 字符 |
| **zh_index RLE 节省** | RLE 节省了若干字节，但收益有限 |

### 10.2 可考虑的优化方向

| 方向 | 预估收益 | 难度 |
|------|----------|------|
| **去掉 cn_index 中冗余映射** | 可省 ~500KB~1MB | 中 — 需处理中文搜索降级 |
| **entry 数据通用压缩（gzip/brotli）** | 省 ~60-70%，但需运行时解压 | 高 — 需解压到内存 |
| **entry 数据二值化（CBOR/MessagePack）** | 省 ~20-30% + 解析更快 | 中 — 需替换 file.readText |
| **inflect 仅保留 eid 版** | 省 ~190 KB | 低 — 搜索端已使用 eid 版 |
| **合并 words/ + entries/ 为单一查找结构** | 省 ~200 KB（去冗余） | 中 — 需重构搜索流程 |
| **用 flatbuffer 替换文本分片** | 省 ~40% + 随机访问 | 高 — 无原生 flatbuffer 支持 |
| **cn_index 改用 bloom filter + 按需回退** | 省 ~1.5 MB | 高 — 需要额外的回退策略 |
| **减少条目数（删除低频词）** | 每删 1000 词省 ~70 KB | 低 — 但影响覆盖 |
