二、原始需求
------------------------------------------------------------

1. 根据 C:\Users\Administrator\.vela\sdk\screenshot 下不同设备分辨率的
   首页截图进行针对性优化。

2. 圆形屏幕使用 2×2 主按钮布局。

3. 矩形屏幕使用 2×2 主按钮布局。

4. 胶囊形/跑道形手环继续使用纵向单列布局。

5. 设备启动时检测屏幕分辨率和形状，自动选择布局。

6. 同一个 RPK 自动适配不同设备，不生成按设备拆分的多个安装包。

7. 不影响其他页面。

8. 保持所有可见文字至少 18px。

9. manifest 的 designWidth 必须保持 "device-width"。

10. 不使用条件编译作为运行时多屏方案。

11. 除非用户明确要求，不启动、不部署、不操作模拟器。

四、关键工程约束
------------------------------------------------------------

1. Vela CSS 只支持有限选择器。

   可使用：
   - .class
   - #id
   - tag
   - 逗号分组

   不应使用：
   - 后代选择器
   - 子选择器
   - 复杂组合选择器
   - 常规 Web 框架专用语法

2. 项目历史中存在重要兼容性证据。

   commit 0a3d512：
   - 提交说明记录 @media (shape: circle/rect) 在目标 Vela 引擎中不受支持。
   - 崩溃表现为原生 Data Abort。
   - 当时通过删除形状媒体查询解决崩溃。

   commit ad7009f：
   - 再次删除 @media (shape: circle)。
   - 目的是保证 JSC 字节码构建与运行兼容。

   commit a4d7d10：
   - 提交标题同样强调删除不支持的媒体查询，防止原生 Data Abort。

   结论：
   即使 aiot-toolkit 能成功编译 shape 媒体查询，也不能证明目标运行时安全。
   本项目不得重新使用 @media (shape: circle/rect/pill-shaped) 作为适配核心。

3. 不应使用条件编译。

   条件编译会按设备类型生成不同构建产物，适用于设备间存在完全不同业务逻辑
   的项目。本需求要求同一个 RPK 在启动时自动适配，所以条件编译方向不合适。

4. 首页必须保持真实组件树。

   不允许用一张首页截图、背景图或预渲染大图代替按钮。所有入口必须继续是
   可点击的 Vela div/text/img 组件，并保留现有路由处理函数。


五、最终技术方案
------------------------------------------------------------

采用：device.getInfo() + 全局屏幕档案 + 首页动态 class。

不采用：shape 媒体查询、条件编译、静态截图替代界面。

总体数据流：

应用启动
  -> src/app.ux 的 onCreate()
  -> device.getInfo()
  -> updateScreenInfo(data)
  -> 保存 screenShape/screenWidth/screenHeight
  -> 计算 screenAspectRatio
  -> 生成 screenProfile

首页初始化
  -> src/pages/index/index.ux 的 onInit()
  -> 先读取 app.ux 中已有的 screenProfile
  -> 再调用一次 device.getInfo()，消除 app 异步回调尚未完成的时序风险
  -> 调用 app.updateScreenInfo(data)
  -> 更新首页本地 screenProfile
  -> Vela 数据绑定更新动态 class
  -> 应用对应布局样式


六、屏幕档案算法
------------------------------------------------------------

全局数据字段：

- screenShape
- screenWidth
- screenHeight
- screenAspectRatio
- screenProfile

档案分类规则：

1. screenShape === "circle"
   -> screenProfile = "circle"

2. screenShape === "rect"
   -> screenProfile = "rect"

3. 其他形状且 screenWidth / screenHeight <= 0.4
   -> screenProfile = "pill-compact"

4. 其他情况
   -> screenProfile = "pill-standard"

宽高比保留三位小数：

Math.round((screenWidth / screenHeight) * 1000) / 1000

目标设备分类结果：

- 192×490，ratio≈0.392 -> pill-compact
- 212×520，ratio≈0.408 -> pill-standard
- 336×480，shape=rect -> rect
- 432×514，shape=rect -> rect
- 466×466，shape=circle -> circle


七、动态 class 结构
------------------------------------------------------------

Vela/aiot-toolkit 支持 class 中插入变量，例如：

class="page page-{{screenProfile}}"

首页节点采用不同前缀，以避开 Vela 不支持后代选择器的问题：

- page-{{screenProfile}}
- title-{{screenProfile}}
- icon-card-{{screenProfile}}
- deco-icon-{{screenProfile}}
- button-group-{{screenProfile}}
- main-button-{{screenProfile}}
- btn-icon-{{screenProfile}}
- bottom-row-{{screenProfile}}
- small-button-{{screenProfile}}

示例：

圆屏最终得到：

- page-circle
- title-circle
- button-group-circle
- main-button-circle
- btn-icon-circle
- bottom-row-circle

紧凑胶囊屏最终得到：

- page-pill-compact
- title-pill-compact
- icon-card-pill-compact
- deco-icon-pill-compact
- main-button-pill-compact
- bottom-row-pill-compact
- small-button-pill-compact

所有 profile 值都来自代码中四个固定字符串，不接受用户输入，不存在动态 CSS
注入入口。

十、为什么首页再次调用 device.getInfo()
------------------------------------------------------------

app.ux 的 onCreate 会先发起设备信息请求，但 device.getInfo 是回调式异步接口。
首页 onInit 执行时，全局回调不一定已经完成。

如果首页只读取全局默认值，圆屏或矩形屏可能先按 pill-standard 渲染，并且全局
普通对象的后续变化不一定自动触发首页局部 ViewModel 更新。

因此首页再次调用 device.getInfo：

- 优点：确保首页自己的 screenProfile 一定在回调中更新。
- 优点：避免复杂事件总线或订阅机制。
- 优点：调用成本很低，仅首页启动时执行一次。
- 缺点：应用启动阶段重复读取一次设备信息。

当前结论：该重复调用是有意的时序保护，收益高于微小开销。


十一、失败回退策略
------------------------------------------------------------

默认 profile 为 pill-standard。

如果 app.ux 和首页的 device.getInfo 都失败：
- 首页仍能稳定显示标准胶囊屏单列布局。
- 所有入口仍然可点击。
- 不会因为空值导致模板崩溃。

代价：
- 极端情况下，非胶囊设备可能暂时显示单列布局。
- 这是稳定优先的回退，不会造成业务不可用。

十六、未来可选优化
------------------------------------------------------------

1. 抽取 profile 分类纯函数

可把 updateScreenInfo 中的档案判断抽成纯函数，例如：

resolveScreenProfile(shape, width, height)

优点：
- 容易做离线测试。
- 便于未来增加新设备档案。

注意：
- 不要为这一个小函数引入复杂模块或构建依赖。


2. 减少重复设备查询

可研究 app.ux 发布 profileReady 事件，首页订阅后更新。

但必须确认：
- 目标设备支持所使用的事件机制。
- 页面销毁时正确取消订阅。
- 不引入比一次 device.getInfo 更高的复杂度和崩溃风险。

在没有充分收益前，保留当前双查询更稳妥。


3. 为更多屏幕建立档案

未来如果出现超宽矩形屏或尺寸更小的胶囊屏，可以在 screenProfile 中增加档案，
但应遵守：

- 先有真实截图或设备数据。
- 不按单一型号硬编码。
- 优先按 shape + aspect ratio 分类。
- 不使用历史已知会崩溃的 shape 媒体查询。


4. 首页视觉微调

实际截图确认后，可仅调整对应 profile class：

- page-xxx
- title-xxx
- button-group-xxx
- main-button-xxx
- bottom-row-xxx

不要修改通用路由逻辑，也不要为了单个设备改动其他页面。
